# Live Offshore Oil & Gas Vessel Activity Pipeline
**A Medallion Architecture on Norwegian AIS Data** — Project definition (check-in)

## 1. Project statement (scope)
**Builds:** a continuously running Bronze → Silver → Gold pipeline (Python collector, PySpark DataFrame/Spark SQL, GitHub Actions) that turns Norwegian open AIS vessel positions into trusted tables of vessel activity around offshore oil and gas installations.
**Need:** raw AIS is a high-rate stream with sentinel values, duplicates and no notion of "installation"; analysts cannot answer *how busy is each installation and how long do vessels stay?* from it directly.
**Outcome:** `vessel_visits` and `installation_activity_hourly` for a dashboard/analyst (e.g. logistics or HSE analyst comparing installation traffic), published only after quality checks pass.
**Out of scope:** vessel-intent prediction, mobile rigs (only fixed Sodir installations), fishing/leisure vessels (not in the open data), emissions or cost modelling, a production-grade dashboard (Gold is dashboard-ready).

## 2. Dataset (source and suitability)
| Source | Access / refresh | Notes |
|---|---|---|
| Barentswatch Live AIS (Kystverket open AIS) | OAuth2 client credentials; HTTP stream `live.ais.barentswatch.no/v1/combined`; continuous | Norwegian EEZ + Svalbard/Jan Mayen; no fishing vessels < 15 m, no leisure craft < 45 m; nothing older than 14 days; NLOD |
| Kystverket HAIS (backfill) | Web order (area, period, ship types) → (Geo)Parquet link | History to 2005; same exemptions; size depends on the ordered box (to be measured) |
| Sodir FactPages | Public shapefile zips / REST; daily update | Installation points, fields; NLOD, attribution required |
**Suitability:** the stream is high-volume, append-only, time- and geo-partitionable, and needs a spatial join plus sessionisation, which is a natural fit for distributed processing. Accumulated size is measured (messages/s, GB/day) by the collector's hourly report and topped up with HAIS backfill.
**Risks:** sentinel values (lat 91, lon 181, SOG 102.3, heading 511), duplicates on reconnect, late data, schema drift (new/renamed fields), self-reported fields (ship type, name, destination) of poor quality, coverage gaps. **Reproducibility:** Bronze is immutable and carries run ID/file lineage; Silver and Gold are rebuildable from it; code, config and a synthetic-data end-to-end run are in the repo.

## 3. Bronze (ingest and preserve)
Long-running collector (the stream never ends, so it is a service, not a scheduled job) writes **one gzip JSONL file every 120 s** to `bronze/raw/dt=YYYY-MM-DD/hour=HH/`, via temp name + atomic rename so Spark never reads partial files. Each line keeps the **raw payload untouched** plus `_source`, `_ingest_ts`, `_run_id`, `_file`. Token refresh and reconnect with backoff; every flush logs files, messages, bytes (raw/gz) and errors; a heartbeat file feeds monitoring. Duplicates and late data are *not* handled here (Bronze preserves what arrived); schema changes cannot break ingestion because the payload is stored as text. Reference data: Sodir shapefiles stored with source URL and ingest time. Testing/deployment: unit tests and a synthetic end-to-end run in CI on every push; merge to `main` deploys over SSH to the always-on host with the `prod` config.

## 4. Silver (primary focus)
**Grain & keys:** one validated position report per vessel per message time, key `(mmsi, event_ts)`; relationship to reference: nearest installation by distance. **Essential** fields: mmsi, msgtime, lat, lon; **optional:** name, ship type, destination, size; **derived:** event/ingest timestamps, latency, nearest installation, distance, near/at-zone flags, stationary flag, `dt`/`hour`; **unreliable:** heading, rate of turn, SOG, ship type, name, destination.
**Cleaning rules (explicit, counted):** *Rejected* (kept in `silver/rejects` with reason): unparsable JSON, MMSI not 9 digits, bad timestamp, missing/sentinel/out-of-range position, timestamp > 5 min in the future. *Corrected to null* (row kept): SOG ≥ 102.3 or < 0, heading 511, rate of turn ≤ −128, ship type 0, blank names. *Deduplicated* on the key (earliest ingest wins), within the batch and against existing Silver. **Standardisation:** typed columns, UTC timestamps, knots/degrees, upper-cased names, explicit schema (unknown fields counted as drift, never fatal).
**Enrichment:** broadcast join to Sodir installations (≤ 5 km "near", ≤ 500 m "at installation" = safety-zone radius), nearest wins.
**Quality evidence:** for every micro-batch, `quality/silver_metrics.jsonl` records input, parse-failed, per-reason rejects, valid, duplicates (in-batch/cross-batch), corrections per field, unknown-field rows, latency p50/p95, reject rate, runtime — i.e. *before* (input, defects) and *after* (accepted) counts that reconcile exactly. Verified against injected defects on synthetic data (docs/EVIDENCE.md).
**Implementation:** DataFrame/Spark SQL functions (`from_json`, `when`, window `row_number`, broadcast join, `percentile_approx`), one small testable function per step; Structured Streaming `availableNow` for incremental, checkpointed, rerun-safe processing every 120 s.
**Performance (evidence-based):** scans = new Bronze files only (checkpoint); the only join is a small broadcast one, so the lever is pairs evaluated: a bounding-box prefilter before the exact haversine cut the join step 2.4× (52k positions) to 6.4× (309k) with identical output; tuning shuffle partitions to 4 gave a further 10–20 %. Gzip JSON is not splittable and 120 s batches create small Silver files (coalesced to one per batch; compaction is the next step). **Lifecycle:** logic is tested in CI, reviewed via pull requests, versioned in Git, deployed by Actions, monitored through metrics. **Scalability:** more volume → larger broadcast-safe reference, more partitions, Delta Lake `MERGE` for dedupe, Kafka instead of files; late data lands in its original `dt` partition and is re-deduplicated by Gold; schema evolution is absorbed by raw-text Bronze plus drift counters.

## 5. Gold (serve the outcome)
**Question:** *Which installations see the most vessel traffic, and how long do vessels stay?* **Consumer:** analyst/dashboard. **Why different from Silver:** Silver keeps every position; Gold is small, aggregated and business-shaped: `vessel_visits` (visit = gap > 30 min starts a new one; arrival, departure, duration, min distance, entered 500 m zone) and `installation_activity_hourly` (distinct vessels, messages, messages in zone, average speed). **Correctness:** Gold totals must equal Silver totals (checked). **Refresh:** hourly, over the last 2 days. **Readiness & failure:** Gold is built in staging and swapped in only if all checks pass, then `gold/_READY.json` is written (status, checks, row counts); on failure the previous Gold stays, `_LAST_FAILED.json` explains why and the job exits non-zero.

## 6. End-to-end delivery
**Run it:** README (clone → venv → `APP_ENV`, credentials → collector + loop; `scripts/run_demo.sh` needs no credentials). **Environments:** `config/dev.json` vs `config/prod.json` (separate data roots, thresholds), selected by `APP_ENV`. **Automation:** CI = static check, unit tests (config, schemas, Silver rules, Gold logic), synthetic end-to-end run with ground-truth assertions, gate test; CD = SSH deploy on merge; monitor workflow every 10 min checks collector heartbeat and Gold readiness. **Why not Actions for the 2-minute run:** scheduled workflows run at most every 5 minutes and can be delayed, so collector and Spark loop run as services on one host. **Visibility:** `scripts/status_report.py`, metrics files, rejects table, manifests. **Ownership:** the author owns code and operations; limits and assumptions are listed in docs/DESIGN_AND_LIMITS.md.
